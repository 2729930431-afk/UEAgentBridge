# Live Coding 与当前会话更新

## 选择编译方式

- UE 已运行：先通过 `unreal` search → describe 查找 Live Coding、控制台与日志能力。当前接口可用控制台 `LiveCoding.Compile` 异步触发编译；先检查 PIE 状态，避免打断用户正在运行的会话。编译及补丁应用属于编辑操作，不要求为此启动 PIE。
- UE 已关闭：查项目 README，使用该项目的标准 Editor 构建入口（若有构建脚本优先使用）。启动仍需当前任务授权。
- 不混用 Live Coding 和传统 Hot Reload，不为绕过 DLL 占用而使用 `-ModuleWithSuffix`、复制/改名 DLL、手改 `.modules` 或强制卸载活动模块。普通函数实现修改通常可热应用；反射类型变化应检查当前引擎的 reinstancing 支持和实际日志，不预判为必须重启。构造函数默认值变化还要检查现有 CDO、蓝图覆盖及已放置实例，不能假设补丁会刷新全部旧实例。

## 验证应用结果

编译前确认项目、目标模块及当前加载 DLL。必要时只读进程模块（PowerShell `Get-Process UnrealEditor` 的 `Modules`）并对比目标 UE 项目 `Binaries/Win64/UnrealEditor.modules`，不要只看磁盘上最新文件。不要输出认证令牌。

触发编译后读取 `system_control.read_log` 的 livecoding、build 和 editor 来源，直到编译和补丁应用明确完成或失败。根据实际日志判定，不能只用固定等待时间。每次等待不超过 60 秒并及时说明进展。

- 必须分别报告“编译通过”和“当前进程补丁已应用”。日志若提示 module not loaded / changes ignored、编译失败或补丁失败，则本次未热生效。
- 可用进程模块中的目标 `*.patch_*.exe` 与最终编辑器应用日志交叉确认。单独的“链接成功”或“补丁创建成功”还不代表应用完成；中途符号诊断也应结合最终结果判断，保留实际限制。
- no changes 仅在确认当前进程本来已是所需代码时才是正常结果；源码已改而当前仍为旧模块时，继续查构建依赖与目标。
- 蓝图或组件变更再通过原生检查接口回读相关状态。没有运行授权时，不用 PIE 验证手感，不把代码加载成功描述为功能运行验证。

## 模块不一致的恢复

若加载 DLL 与构建目标不一致，先查是否混入编号热重载模块、错误项目或错误配置，以及 Live Coding 当前编译目标。优先使用编辑器支持的正确目标与补丁路径；不要反复重复无效编译，也不要修改桥接认证/传输配置来修复编译目标。

若已经混入编号模块，且当前接口不能安全修复加载基线，应明确说明这是编译/加载状态不一致；只有拿到本次重启授权后，保存 → 原生关闭编辑器 → 确认进程退出 → 标准无编号构建 → 启动 → 核实加载标准模块及连接恢复。这是恢复受损基线的措施，不是后续普通修改的默认流程。

桥接自身模块被修改时，先判断补丁是否会影响当前请求处理与反射注册，异步触发并在请求结束后检查日志、连接和实际补丁结果。只有具体错误证据才支持报告接口缺陷；不要为了“增加热加载能力”绕过已可用的 Live Coding 控制台接口。
